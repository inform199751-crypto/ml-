# 🍷 餐酒館智慧推薦與營運分析系統

> 推薦系統推的不是「客人最可能點的」,而是「**客人會接受、且最賺錢的**」。
>
> 一般推薦系統的目標是命中率;餐飲營運的目標是**每桌毛利**。這個專題把後者做成可執行的系統。

---

## 這個專題在解決什麼問題

餐酒館的獲利結構和一般餐廳完全不同:**主食毛利低(35–45%),真正賺錢的是酒水(57–80%)**。主食的角色是「帶客」,靠招牌菜把人拉進來;毛利要靠加點的 tapas 與酒水補回來。

所以外場最關鍵的能力,是在客人點完餐的那 30 秒內,推出**一杯客人會接受、又能賺錢的酒**。

但這件事在現場很難穩定做到:

- 新進外場不知道什麼餐配什麼酒
- 資深外場憑感覺推,推的常是自己熟的那幾款,不一定是毛利高的
- 沒有人知道「這杯推出去,期望能賺多少」

這個系統就是把這個判斷變成可量化、可重複、可訓練的流程。

## 核心架構:三階段推薦

| 階段 | 做什麼 | 方法 |
|---|---|---|
| **① 召回** | 找出所有與已點餐點有關聯的酒款 | Apriori 關聯規則(support / confidence / lift) |
| **② 排序** | 依「**期望毛利**」排序,而不是「加點成功率」 | 期望毛利 = confidence × 售價 × 毛利率 |
| **③ 重排** | 用**餐飲專業規則**把關 | 搭配禁忌 / 時段調整 / 推薦多樣性 |

### 為什麼用「期望毛利」而不是「加點成功率」

| | A 酒 | B 酒 |
|---|---|---|
| 加點成功率 | 60% | 40% |
| 單杯毛利 | 100 元 | 266 元 |
| **期望毛利** | **60 元** | **106 元** |

結論是該推 B,即使它「比較難成功」。多數推薦系統會選 A —— 推薦成功了,卻沒賺到錢。

### 為什麼需要第三階段(這是本專題的核心差異)

開發過程中模型算出:「香煎鮭魚佐檸檬」應該配「**Negroni**」—— 因為 Negroni 毛利最高,統計上也常被一起點。

**但這在餐飲上是錯的。** Negroni 是苦艾酒 + 金巴利的重口味調酒,苦韻會直接蓋掉鮭魚的細緻風味,還會把海鮮的腥味帶出來。這杯酒推出去,客人喝一口就放下,下次不會再來。

> **模型看得到「一起被點」,看不到「客人喝完的感受」。**

第三階段(`business_rules.py`)就是把餐飲專業知識寫成規則替模型把關:

- **R1 搭配禁忌**:風味衝突的組合直接排除,每一條都附實際理由
- **R2 推薦多樣性**:三杯不能都是調酒 —— 不喝烈酒的客人一杯都不會點,轉換率反而是 0。實務做法是「一支酒 + 一支啤酒 + 一個無酒精」,讓桌上每個人都有東西可以點
- **R3 時段調整**:21 點後調酒加權;23 點後紅酒降權(收攤前不推需要慢慢品的酒)

介面上可以一鍵切換「有 / 沒有餐飲規則」,直接看出差異。

## 資料分析的主要發現

分析期間 2026-02-01 ~ 2026-06-30,共 1,812 桌、14,181 筆訂單明細、28 個品項。

| 發現 | 數據 | 營運含義 |
|---|---|---|
| **酒水貢獻近半毛利** | 酒水佔總毛利 **46.1%**,酒水營收佔比 **39.5%** | 酒水是這門生意的引擎,不是配角 |
| **到店時間是雙峰,不是單峰** | 19 點(晚餐峰)、21–22 點(微醺峰) | 一般餐廳只有一個峰。**第二峰的客人是來喝的,不是來吃的** —— 兩批客人要用不同的服務腳本 |
| **越晚酒水佔比越高** | 21 點後 **47.4%** vs 21 點前 **27.1%** | 推酒的力道應該隨時段遞增,不是全天一致 |
| **停留越久喝越多** | 停留時間與人均酒水杯數正相關 | **餐酒館不該追求翻桌率** —— 這和一般餐廳的營運邏輯完全相反,是這門生意最關鍵的認知 |
| **11.1% 的桌完全沒點酒水** | 零酒水桌佔 11.1% | 這些是流失的毛利,也是最明確的改善標的 |
| 平均客單價 | 950 元 | — |

毛利貢獻 Top 5:炭烤戰斧牛排、Old Fashioned、伊比利火腿盤、三種起司拼盤、Negroni ——
**五名裡有兩杯是調酒**,這正是餐酒館的獲利結構。

## 叫貨建議:為什麼「賣最好的菜最容易斷貨」

`model_inventory.py` 回答店長每天下午都要做一次的決定:**今天要叫多少貨?**

```
日均銷量 × 前置期 + 安全庫存 − 現有庫存 = 建議叫貨量
                                  且不得超過「保存期限內賣得完」的上限
```

四個設計決策都來自餐飲現場,不是教科書公式:

| 設計 | 為什麼 |
|---|---|
| **日均銷量排除公休日** | 這家店週一公休。直接用「總銷量 ÷ 天數」會讓分母多算 1/7 的零銷售日,日均低估約 14%,叫貨系統性偏少。128 個營業日 ≠ 150 個日曆日 |
| **ABC 分級用毛利,不用銷量** | 松露薯條賣得比戰斧牛排多,但一份薯條毛利 130 元、戰斧牛排 308 元。用銷量分級會把撐起這家店的品項排到後面 |
| **服務水準分級(98% / 95% / 90%)** | 招牌菜斷貨的代價 ≠ 冷門菜斷貨的代價。**「賣最好的菜最容易斷貨」的根因就是大家用同一把尺備量** |
| **保存期限是硬上限** | 海鮮能放 2 天,酒水能放一年。酒水可以囤(囤了還能撐過缺貨),生鮮囤了就是廚餘。這是餐酒館的結構優勢 —— 毛利最高的品項剛好最耐放 |

分級結果:**A 級 15 品項貢獻 67.5% 毛利**、B 級 7 項佔 22.2%、C 級 6 項佔 10.2%。

執行結果的紅燈清單前四名全是生鮮 A 級品項(炭烤戰斧牛排、爐烤伊比利豬肩、西班牙蒜辣蝦、舒肥紅酒燉牛肉)—— 這正是「銷售冠軍反而先斷貨」的實例。

### 一個開發過程中修掉的錯誤

第一版不分品類,一律讓熱銷品只剩不到一天的量,結果 **28 個品項有 24 個被標成「立即叫貨」**。

**全部都紅等於沒有紅** —— 店長看一次就不會再看第二次。這叫**提醒疲勞**,也是導入的系統上線一個月就被棄用的頭號原因。

根因不在演算法,在假設不合現場:餐酒館的酒是**按箱囤**的(前置期 5 天又不會壞),庫存本來就有好幾週;只有生鮮才會被盤到剩不到一天。改成依保存期分三層之後,紅燈收斂到 6 項,而且全部是真的該處理的。

### 庫存必須由人盤點,系統不該假裝知道

`reorder_advice()` 的庫存是**參數輸入**,不是系統算出來的。

因為 POS 只知道「賣掉幾份」,不知道試菜、員工餐、掉在地上、切壞的那幾份。**以為串了 POS 就能自動算庫存,是系統導入時最常出錯的地方。** 庫存永遠以實際盤點為準。

## 專案結構

```
bistro_ai/
├── config.py            # 菜單與營運參數(毛利結構、時段權重、風味搭配矩陣)
├── data_generator.py    # 模擬資料產生器(依餐酒館實際運作行為建模)
├── eda.py               # 探索性分析與圖表輸出
├── model_basket.py      # 關聯規則挖掘(Apriori)
├── model_segment.py     # 客群分群(KMeans)
├── model_upsell.py      # 高酒水潛力桌預測(Logistic Regression)
├── model_inventory.py   # ★ 銷售預測與叫貨建議(ABC 分級 / 安全庫存 / 廚餘風險)
├── business_rules.py    # ★ 餐飲商業邏輯層(禁忌 / 時段 / 多樣性)
├── app.py               # Streamlit 互動介面(點餐推薦 + 營運儀表板)
├── data/                # menu.csv / order_items.csv / visits.csv
└── output/              # 圖表與分析結果
```

## ⚠️ 資料聲明

**本專題使用模擬資料**(150 天、約 1,800 桌)。真實餐廳 POS 資料屬營業機密,公開資料集中沒有餐酒館的完整消費紀錄。

但模擬資料的**行為規則全部依照餐酒館實際運作設定**,參數來自我本人的餐飲現場經驗:

- 雙峰到店時間分布(晚餐峰 + 微醺峰)
- 各品項的毛利結構(主食低、tapas 高、酒水最高)
- 停留時間與酒水杯數的正相關
- 風味搭配傾向矩陣(`PAIRING_AFFINITY`)
- 常客與新客的消費差異
- 週五六的來客強度倍率

**資料是模擬的,但營運邏輯是真的。** 因此本專題的分析方法可以直接套用到真實 POS 資料,數值本身僅供方法演示。
